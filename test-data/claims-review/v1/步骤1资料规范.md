# 步骤 1：数据格式、审查规则与条款目录

本步骤完成待准备清单 G02–G07，用于统一后续制作 C01–C16 案件和标准答案的口径。文件状态为“准备规范已生成并经过离线校验”，不代表业务 Agent 已接入这些格式或真实效果验收通过。

本步骤未生成任何 C01–C16 案件、未导入数据库、未建立向量索引、未调用模型或 Embedding，也未处理已跳过的索赔申请书模板。

## 2. 三类数据严格分开

| 文件类型 | 放什么 | 不放什么 |
| --- | --- | --- |
| `inputs/Cxx/case.json` | 原赔案事实、记录、原处理意见、材料目录与来源 | 预期疑点、人工提前标注的正确答案和未来补件 |
| `expected/Cxx.json` | 人工预先标注的预期发现、禁止误报、证据、检查覆盖和各阶段预期结果 | 不能作为 AI 输入或进入知识检索 |
| `review-steps/Cxx.json` | 人员何时查看证据、选择结论、补资料、修订意见及保存报告 | 不能作为原理赔历史事实提前输入 AI |

Schema 使用明确字段并拒绝额外字段。把 `expectedFindings` 等答案字段加到案件输入会失败。字段格式正确不代表事实真实或证据充分；事实和结论质量仍须按实际资料另行验收。

## 3. 案件数据的组织方式

`case.json` 的主要字段如下。除明确允许为空的值外，字段结构需要齐全；没有相关记录使用空数组，不能用省略整个类别的方式制造歧义。

| 字段 | 作用 |
| --- | --- |
| `datasetCaseId`、`caseRevision` | 主案或变体编号及不可混用的输入版本 |
| `reviewScope` | 目标赔案、仅作关联参考的赔案、车损类型和范围限制 |
| `accident` | 事故时间、地点、经过及原责任记录 |
| `parties`、`vehicles` | 当事人、车辆及本车/第三方身份关系 |
| `claims` | 同一事故下的赔案、结案类型、原结论和支付状态 |
| `policies` | 已取得、未取得、已确认未投保或无法识别的保单；实际承保险种放在各保单的 `coverages` 中 |
| `endorsements` | 批改、特别约定及其影响的保单和险种 |
| `losses` | 分车辆或人员的损失及各金额口径 |
| `calculations`、`approvals` | 分项理算及原核赔记录；保留有效、草稿、被替代等状态 |
| `payments` | 付款、退款和冲销事件及其审批分配、原交易关系 |
| `documents` | 案件文件、归属、版本、路径、页数、hash 和取得情况 |
| `evidence` | 统一证据定位：案件 PDF、公共文件或带来源的结构化业务记录 |
| `observations` | 同一事实在不同来源中的原始值和归一化结果，用于保留冲突或非法原值 |
| `dataGaps` | 资料未取得、确证原作业未收集、字段未知、冲突未决等缺口 |
| `knowledgeRefs` | 本次固定的公共条款文件、版本、hash 与正文分节 |
| `injury` | 原案件的人伤声明和已记录伤者；不是 Agent 的最终识别结论 |

人员、车辆、赔案、保单、险种、损失、计算、审批、支付和证据均使用稳定编号关联。编号必须存在且唯一，不能把另一个案件中不存在的对象作为引用。

不同记录的金额矛盾或同一事实的来源冲突是允许的测试输入，不因“业务有问题”而拒绝加载。不存在的引用、越界页码和文件 hash 不符属于资料完整性错误，应当先修复或明确作为负向格式测试。

## 4. 金额、未知值和时间

### 4.1 金额

统一以整数分保存，币种固定为 CNY。已知零元与未知金额分别表达：

```json
{"status": "known", "amountFen": 0, "currency": "CNY", "reason": null}
```

```json
{"status": "unknown", "amountFen": null, "currency": "CNY", "reason": "本次档案尚未取得对应计算书"}
```

金额不允许小数分、负数或超出 JavaScript 安全整数范围。付款、退款、冲销均保存非负金额，收付方向由交易类型表示。费率使用基点（10,000 基点表示 100%），不自行填入合同未明确的免赔值。

未知金额必须有原因，不能用零元填补。不适用的金额口径使用`status=not_applicable`、`amountFen=null`并说明理由，与未知分开。保险金额、责任限额、免赔金额也不能混用。

### 4.2 时间与冲突原值

规范时间使用带时区的 ISO 8601，例如 `2026-09-01T12:00:00+08:00`。只有日期、时间未知或原值无效时，不自动补成零点；规范时间留空，原值放入 `observations`，并记录相关缺口。

原值 `2026-13-40` 可以作为无效观察保存，但不能放进已经确认的规范时间字段。不同来源给出不同时间时分别保留，不覆盖为单一模型推断结果。

## 5. 证据、文件与条款定位

- 案件材料路径相对于该案目录，使用 `/`，不使用盘符、绝对路径或 `..` 跳出目录。
- PDF 页码从 1 开始，文件版本、SHA-256 和页数均需保存。状态为“未取得”的材料不能伪造文件路径、hash 或页码。
- `case_document` 和 `shared_document` 证据定位到对应文件版本及页码；`structured_record` 定位到案件 JSON 中真实存在的 JSON Pointer，并标明原始结构化记录或人工转录来源。
- 人工转录不自动等于独立原始凭证；证据语义支持仍需原文和人工检查。证据不能通过引用另一个证据条目形成自我证明。
- `clause-catalog.json` 保留来源清单中的真实版本和 hash，不把条款改名成年份不实的新版本。
- 正文分节用 `sectionId` 标识；同一页可以包含多个分节，因此同时记录页码、正文锚点和提取行号。条文编号在不同附加险中会重复，须连同分节一起使用。
- 附加险的编号目录与实际正文标题分别处理；目录中出现险种名称不能作为责任依据。
- 通用章节随实际适用的险种提供。车损险、三者险不能因为都在同一 PDF 中就混用责任。
- 产品目录、服务规范和空白模板保留用途分类，不作为保险合同责任正文。
- 提取工具及版本已固定记录在目录中。PDF hash 不变但提取器变化时，应重新核对目录，不能假定旧行号仍正确。

## 6. 人工复核脚本与报告门禁

`findingKey` 是标准答案中的稳定逻辑键。实际测试时先按对象、含义和证据匹配 AI 发现，再映射实际运行 ID，不要求模型生成固定随机编号或逐字输出标准答案。

支持的操作有：查看疑点、首次决定、修改决定、补充证据、人工新增疑点、记录专业意见、确认检查覆盖、保存报告和显式启动重新分析。

- 确认问题、排除疑点必须先由该操作人查看相关证据，并保存有内容的意见和依据。
- 修改已有决定使用 `amend_decision` 并说明原因，不能冒充首次决定覆盖历史。
- 待补件必须说明缺什么和跟进对象；转专业必须说明原因和接收对象。
- 专业意见的录入本身不将事项改为已解决，后续仍需明确作出复核决定。
- 补充资料使用新的证据标识；不能覆盖首次输入中的同名证据。若让 AI 重读新材料，应另起输入版本和分析任务。
- 同一幂等键的相同请求可以返回原结果，不能新增重复决定；请求内容不同不能当作同一次成功提交。
- 车损和影响车损的共用事实仍未决时，只能形成阶段报告；不能把发现移到“人伤”类别来绕过门禁。
- 人伤本身属于范围外，独立人伤专业转交可以未决，但最终车损报告要明确披露。共用事实影响车损时仍需核实。
- 无疑点案件也必须人工确认检查覆盖；自动执行完成不等于最终报告完成。

标准答案保存 `initialCheckpoint` 和后续 `reviewCheckpoints`，分别定义各阶段发现状态、检查覆盖、报告类型和最终报告是否允许。初始状态不能直接预填为人工已确认。

## 7. 规则表的边界

16 条规则定义了缺失、无效、冲突、保单取得及适用、条款绑定、明确算术、金额调整、有效支付、重复线索、人伤范围和最终报告门禁。规则编号是本项目编号，不是平安内部规则编号。

实际支付净额必须在交易状态、审批分配、退款冲销关联明确时计算；状态或关系不明时保留待核实，不能简单将所有记录相加或扣除两次。计算差额是事实线索，不自动等同于多赔、少赔或违规。

条款语义支持、维修必要性、价格合理性和复杂批单解释明确列为需要证据辅助或专业核实的内容。规则文件不是已实现的业务执行引擎，也没有加入未经取得的内部制度或自动拒赔、补赔规则。

## 8. 离线验证与维护方式

在项目根目录执行：

```bash
node test-data/claims-review/v1/tools/validate_step1.mjs --self-test
```

这个命令检查共享文件、Schema、字典一致性、源文件 hash，并以内存构造的正反例验证格式和关键关系。不会写入 C01–C16，不调用模型或数据库。已覆盖答案泄漏、未知金额、错误时间、断链引用、条款错配、无证据确认、并发脚本预期、幂等和提前定稿等边界；不是应用端并发或真实模型效果验收。

目录与生成文件一致性检查：

```bash
./.venv/Scripts/python.exe -X utf8 test-data/claims-review/v1/tools/build_step1.py --check
```

生成文件的权威维护入口是 `tools/build_step1.py`。修改定义后显式运行下列命令重新生成并复验，避免只改单份 JSON 造成枚举或版本漂移：

```bash
./.venv/Scripts/python.exe -X utf8 test-data/claims-review/v1/tools/build_step1.py
node test-data/claims-review/v1/tools/validate_step1.mjs --self-test
```

后续案件文件准备完成后，可以校验一组实际输入、答案和操作脚本：

```bash
node test-data/claims-review/v1/tools/validate_step1.mjs \
  --case test-data/claims-review/v1/inputs/C01/case.json \
  --expected test-data/claims-review/v1/expected/C01.json \
  --steps test-data/claims-review/v1/review-steps/C01.json
```

上述 C01 文件目前尚未生成，命令只是后续调用方式。脚本进行格式、引用、文件 hash 和计划操作关系校验，不代替 PDF 全文、计算合理性、专业意见真实性或 AI 语义准确率的检查。
