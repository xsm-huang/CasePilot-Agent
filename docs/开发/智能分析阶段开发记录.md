## 本轮开发步骤与原因

1. **先核对现状。** 对照代码、设计与验收要求，确认工作台分析仍是 V0，不能把目录重组或独立知识库当成真实 Agent 已完成。本轮只读检查时开发库有 3 条 completed 历史任务，没有待审任务。
2. **固定事实和知识范围。** 新分析组件保存案件快照、险种、版本、generation、Embedding profile、模型和提示词版本。重复运行沿用保存的上下文，发布新知识版本不改变旧任务来源。
3. **实现真实工具。** query_case 与 validate_materials 是图中的必经 LangChain StructuredTool；模型只能申请 search_clauses 的 query，案件和知识元数据由服务端闭包绑定。
4. **加强确定性规则。** V1 分别识别缺失日期、非法日期、事故早于生效及案件/材料日期冲突；每项发现保留 factRefs 和原值。V0 规则未替换，避免未经协议升级改变现有演示。
5. **新增聊天适配。** 分开真实 tool_call 和 JSON 请求，限定长度、请求次数、模型与单次工具数量，拒绝错误结构、未知工具和截断结果；不自动重试，不展示 reasoning_content。
6. **建立有界图。** 查询 → 规则 → 初检 → 模型决策 → 至多两次补检 → 结构化分析。重复问题或无新增依据提前停止并标记证据不足，不回退关键词库。
7. **校验引用。** 仅允许当前事实与检索片段 ID；险种、版本和 generation 严格匹配，文件名/页码/原文由检索结果提供。结构或引用失败最多修复一次，仍失败则明确报错。ID 有效不代表语义支持，语义验收仍单独进行。
8. **调用前持久占用。** TaskLedger 在请求前保存计数与 reserved 记录；全局最多 8 次模型请求，初检加补检最多 3 次，为报告预留 3 次模型调用。失败和中断不清零，已提交结果复用，未知结果的请求禁止自动重放。
9. **先验证再切换入口。** 当前组件要求有持久仓储；内存演示入口不会自动调用真实模型。现有 API、工作台和旧报告保持原协议，切换方案单独列出供确认。

## 验证范围与已知限制

- 41 项首批组件测试通过；随后新增生产入口拒绝内存存储的检查，并单独通过全部 10 项图测试。
- 真实 LangChain 对空参数 Schema 默认跳过校验，本轮加入 ScopedTool 显式校验并保留回归，避免额外案件参数被静默忽略。
- 使用真实 PostgreSQL、文字 PDF、pgvector 和独立进程验证：G3 图读取真实索引元数据；新发布后原任务仍使用旧 generation；已提交结果跨 Store 重载不重复调用。
- 独立进程持久账本验证：完成请求后重启复用结果；另一请求预占后强杀；重启拒绝静默重放；显式新 attempt 后总额度为 3，没有重置或返还。
- 模型和向量来自注入替身或 HTTPX MockTransport，不证明真实模型工具能力、Embedding 质量、语义支持或实际 token 成本。
- G3 组件尚未挂入正式 HTTP 执行器；当前不生成最终模型报告、不创建会话、不替代 V0 SSE，也没有把 needsReview 冒充已实现的审核中断。
- 最终完整后端回归：167 通过、无跳过，83.53 秒；相对上一阶段新增 44 项，覆盖图/工具、事实规则、引用、聊天适配、预算、真实数据库和独立进程。
- 前端与契约 15 项、契约生成一致性、构建、Ruff 检查/格式检查及文档链接检查均通过；没有修改现有 HTTP 契约生成产物。
- 真实模型探测维持上次未通过的状态，本轮未发送供应商请求。保留既有 PDF 解析依赖弃用提示和 Node 类型转换实验提示，未将其隐藏或标成新功能失败。
