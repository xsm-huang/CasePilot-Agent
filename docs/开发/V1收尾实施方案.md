# V1 收尾实施方案

冻结日期：2026-10-27。本文用于完成当前已批准的 V1，统一前端、后端和测试的改动方向。实施期间不再重构已经通过离线和数据库验证的会话、Agent、审核、报告与恢复主链路。

## 1. 当前基线

V1 产品主链路已经存在：PostgreSQL 会话与消息、初始分析和追问、固定案件及知识上下文、有界 Agent、人工审核、三节报告、持久 SSE、引用前后文、显式恢复和知识索引发布。当前模型固定为 `glm-5.3-flash`，Embedding 固定为 `embedding-3` / 1024 维。

剩余工作分为两类：

1. 在真实调用前修正前端审核信息、引用请求隔离以及验收工具的预算、恢复和证据产物。
2. 在同一冻结代码、配置和数据基线上完成真实模型、检索、报告、浏览器与恢复验收。

历史 `glm-4.7-flash` 运行记录只作为历史失败证据保留，不能证明当前模型通过。真实验收必须写入新的运行目录，旧产物不得覆盖。

## 2. 冻结范围与契约

- 业务标识保持 `caseId → conversationId → analysisId`；V0 报告永久只读。
- 会话固定案件快照、知识 generation、Embedding profile、模型和提示版本；配置变化后新建会话。
- 会话消息按时间正序返回，`nextBefore` 只属于当前会话；`analysisIds` 按任务创建顺序返回。
- 同一会话最多一个活动任务；`waiting_review` 和 `recoverable` 仍属于活动状态。
- 创建会话返回 201；创建分析、审核和恢复返回 202。幂等键、`expectedRevision` 和 `interruptKey` 保持不变。
- 审核和恢复命令被接受时，状态与 revision 在同一业务事务中推进；前端随后从权威快照和 SSE 继续追平。
- 任务状态、SSE 事件判别字段、连续 seq、单调 revision、终态补发规则保持不变。
- 报告章节固定为 `summary / findings / recommendations`；三节全部验证并提交后才形成最终报告。
- 事实和引用 ID 必须属于当前任务；引用上下文固定同一 generation、文档、险种和版本，相邻段落只辅助阅读。
- 单任务预算保持 8 次模型、3 次检索和 1 次结构修复；供应商请求不自动重试，不静默切换模型。
- PostgreSQL + pgvector、单业务 schema 单 API worker 的部署边界保持不变。

## 3. 三角色所有权

| 角色 | 本轮所有权 | 不在本轮修改的内容 |
| --- | --- | --- |
| 前端 | 审核依据展示、引用请求隔离、事件穷尽处理、页面和浏览器验证 | 后端状态机、共享传输模型来源、业务规则 |
| 后端 | 真实验收运行器、共享预算、阶段恢复、基线清单和评测产物 | 已通过的工作台 API、Agent 主图、持久化主结构 |
| 测试 | 冻结数据校验、T01–T26 执行清单、自动与人工证据审查 | 为获得通过而改题集、标签、阈值或业务提示词 |

共享契约由后端 Pydantic 模型单向生成。若真实门禁暴露协议问题，只修改模型适配层并同步契约测试；不得由前端复制或猜测 DTO。

## 4. 固定实施批次

### 批次 A：真实调用前加固

- 前端完整展示规则严重度和来源原值、模型事实与引用、待补充事项及报告事实引用。
- 引用 A/B 快速切换时，迟到的 A 不得覆盖用户最后选择的 B。
- SSE reducer 显式处理全部事件类型，新增未知事件在类型检查或运行时校验处失败。
- 真实验收使用跨运行共享预算账本；新输出目录不能重置总额度。
- 运行器保存阶段 checkpoint，并能在同一 schema 与输出目录安全恢复；模糊或已停止的供应商账本不可绕过。
- 报告先执行十个样本的第一轮并完成审查，再执行第二、三轮。
- 产物包含源码基线、锁文件与数据哈希、结构化人工语义审查、浏览器检查和恢复检查。

本批次禁止真实供应商请求。

### 批次 B：离线与数据库基线

依次通过 Python 常规测试、契约生成检查、契约与前端测试、类型和构建、Ruff，再运行隔离 schema 的完整数据库与独立进程测试。任一失败先在对应层修复，不进入付费阶段。

### 批次 C：当前模型最小门禁

按工具调用、JSON 对象、1024 维 Embedding 的顺序执行三个最小请求。任一请求出现连接、超时、鉴权、额度、繁忙、格式或能力错误，立即冻结账本并停止后续真实批次。

### 批次 D：真实检索

导入冻结条款与干扰版本，执行 24 道题。通过条件为有答案题 Hit@4 至少 90%，且错险种、错版本、错 generation 和错 profile 数量为零。失败时只检查分块、查询和查询构造，不修改题集或标签迎合结果。

### 批次 E：真实报告与人工语义审查

先运行十个样本各一次。人工确认规则保留、关键结论有原文支持、无依据问题明确保留不确定性、提示注入无效后，再运行第二和第三次。结构合法或引用 ID 合法不能替代语义审查。

### 批次 F：浏览器与真实恢复

在同一 kept server、schema 和预算账本上验证初始分析、审核通过和驳回、三节增量、两轮追问、会话快切、断流重连、知识版本替换及历史引用。最后验证真实供应商在途的模糊调用与恢复边界，避免提前使整批账本进入 fail-stop。

### 批次 G：证据归档

逐项关闭 T01–T26，更新实施状态和当前模型验收记录。任何一项仍为 `blocked`、`skipped`、`not_reviewed` 或 `manual_review_required` 时，不宣布 V1 完成。

## 5. 按失败层修改

| 失败位置 | 允许集中修改 | 避免同时改动 |
| --- | --- | --- |
| 模型协议 | `model/profiles.py`、`config.py`、`chat.py`、`probe.py` | 检索、状态机、页面结构 |
| 检索召回 | `knowledge/pdf.py`、`repository.py`、查询构造 | 评测标签、报告状态机 |
| 报告质量 | 提示词、Agent 输出校验、章节生成 | 分块、接口、会话状态 |
| 页面交互 | 页面组件、composable、事件 reducer | 后端业务语义 |
| 恢复一致性 | 命令对账、调用账本、checkpoint 投影 | 通过隐藏页面状态规避问题 |

每次只修复门禁已经证明的问题，并重跑该层及其下游相关测试。新的业务范围需要另行设计，不混入 V1 收尾。

## 6. 完成定义与范围外事项

同一冻结基线下，离线、数据库和前端回归全绿；当前模型能力门禁通过；24 题达到阈值且无范围污染；十个报告样本各三次的关键无依据结论数为零并完成人工审查；真实浏览器与在途恢复通过；T01–T26 全部具有可复核的通过证据，才算 V1 完成。

真实案件录入与附件抽取、OCR、登录与权限、多租户、多实例工作流、通用多模型平台、报告导出通知和自动赔付均不属于本轮 V1。
