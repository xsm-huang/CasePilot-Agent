# 内部架构检查与整理

本页保留结构整理时的历史检查与原因。V1 接入后已删除旧图、模板报告和关键词库，当前目录职责见 [项目结构与维护规范](项目结构与维护规范.md)，变更原因见 [工作台接入开发记录](工作台接入开发记录.md)。

日期：2026-10-23。范围：Python 服务端内部职责和依赖方向整理；基于上一轮已整理的仓库结构继续工作，保留此前未提交的功能改动。

## 检查结论与采用原则

Agent 项目没有统一强制的目录标准。本项目采用适合现有 FastAPI + LangGraph 单进程应用的组织方式：传输边界、应用用例、工作流、模型适配、知识管线与持久化各有职责。目录对应实际实现，不通过创建空的 tools/prompts/agents 文件夹声称具备真实模型能力。

检查发现原 `main.py` 同时负责路由、数据库、checkpoint、worker 和恢复；原 `workflow.py` 同时承担状态、节点、图、报告和执行器；原 `model.py` 同时处理配置、网络请求、向量与命令；原 `cases.py` 混合演示数据、规则和检索。服务与仓储还直接抛 FastAPI HTTPException，业务错误被绑定在 HTTP 框架上。

## 每一步的意图与原因

| 步骤 | 实施内容 | 意图与原因 |
| --- | --- | --- |
| 1. 审计依赖与入口 | 检查实际源码、测试、调用路径、运行入口和现有数据库约束 | 按真实职责拆分，不把纯粹移动文件当作架构规范化 |
| 2. 建立持久状态基线 | 旧实现创建真实 PostgreSQL 待审核任务后强制停止进程 | 普通“新代码启动两次”的恢复测试不足以证明本次移动能读取旧 checkpoint |
| 3. 收缩应用入口 | `main.py` 仅保留 create_app、路由、错误映射和中间件装配；生命周期放入 bootstrap | 分开 HTTP 装配与资源启停；便于独立测试多个应用实例 |
| 4. 抽离传输层 | 路由统一进入 api；analysis service 处理创建与审核用例，API 处理 JSON/HTTP/SSE | 应用服务可脱离 Request 对象调用，业务不直接操纵响应 |
| 5. 拆分工作流 | workflow/state、nodes、graph；analyses/executor、worker、report | 图只描述节点和边；节点负责副作用；命令恢复与纯报告函数可分别理解 |
| 6. 拆分案件与演示检索 | cases/seeds、repository、rules；关键词库进入 knowledge/demo | 规则保持纯函数，演示数据和真实 PDF/向量库在命名上清楚区分 |
| 7. 拆分模型边界 | model/config、errors、transport、embeddings、probe 和 __main__ | 配置不发请求、异常不泄露原始响应，生产向量请求与手动能力探测各有入口 |
| 8. 抽离持久化 | persistence 负责资源、事务、迁移和只读数据库检查；analyses/store 保留内存投影、稳定事件键与锁 | SQL 不混入路由或图；数据库事务和图 checkpoint 两个提交边界明确保留 |
| 9. 修正依赖方向 | 业务、知识库服务/仓储改为应用异常；api/errors 统一映射旧状态码和响应 | 不依赖 FastAPI 也能执行规则、服务、图或组件测试；外部协议保持不变 |
| 10. 独立传输模型 | Pydantic 模型集中 schemas；export_schema 更新导入 | 导出 Schema 不应初始化数据库、图或应用；生成文件无需变动 |
| 11. 同步测试与文档 | 内部测试检查精确业务错误码，HTTP 测试仍检查状态码；补充架构依赖与实例隔离测试，更新源码链接 | 内部异常重组不能靠放宽外部断言通过，架构边界也需要持续回归 |
| 12. 验证旧状态可恢复 | 新实现读取步骤 2 的原快照并审核通过 | 验证同一任务、原事件、旧 checkpoint 及副作用去重键仍兼容，完成后只清理 UUID 测试 schema |

## 依赖与不变条件

- main/bootstrap 负责装配；api 可以调用应用服务，业务与存储模块不得反向导入 api/main/bootstrap 或 FastAPI。
- graph 只表达拓扑，nodes 使用规则、检索和报告函数；executor 接收已经编译的图，不在执行器中构建运行环境。
- model 不依赖具体工作流或路由；知识库生产 Embedding 由 bootstrap 注入，测试继续注入替身。
- 连接池、数据库与 checkpoint 资源由同一个生命周期退出栈关闭；后台任务先取消，再释放资源。
- 图节点名、条件分支命名、thread_id、状态字段和稳定副作用键保持原值；SSE 格式、接口路径、错误状态码及响应形状保持原协议。
- 表名、字段、迁移版本、发布指纹、profile、数据库 schema、advisory lock 键及事务边界保持原值，不新增业务迁移。
- 原六个聚合文件已由对应模块替代，知识库路由迁入 api；不留下旧目录转发层。model 包保留已有公共适配器函数与显式探测命令，兼容当前本地诊断脚本。

## 特殊情况与确认边界

本次没有需要改变外部接口、数据库数据结构或技术选型才能完成的重组，因此未扩大业务范围。以下项目属于已有边界，保留现状；如要改变，先说明具体方案和影响，再由用户确认：

1. **当前分析仍是 V0。** 关键词检索、直接函数调用与模板报告保持原行为；新建真实 LangChain Tools、模型补检、提示词或多轮会话属于功能实施，不能借结构整理悄悄接入。
2. **知识库保持独立。** 接入案件图需要决定 generation 固定、引用、预算和失败语义，本次不改变分析来源。
3. **单 worker 限制保留。** Store 使用进程内投影和锁，扩展多实例需要重新设计并发与状态来源，不能只修改 workers 数量。
4. **发布和重试事务不继续机械拆分。** knowledge/repository 保留 CAS、幂等与发布指针的事务一致性；提取迁移只移动原 SQL，不改变提交边界。
5. **模型探测仍显式启用。** 本次验证使用替身，不发送真实供应商请求；后续真实服务评测按预算和现有批准范围执行。
