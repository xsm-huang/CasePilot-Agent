# 案件查询与详情页设计

状态：已实现并完成离线回归  
日期：2026-10-28  
适用数据：`test-data/claims-review/v1/inputs/C01` 至 `C03`

## 1. 目标与边界

本阶段只完成已结案车险赔案的查询和只读详情查看，使审查人员能够：

1. 按赔案号、报案号、车牌号查询 C01–C03。
2. 按结案时间、原档案人伤标记、最近审查状态筛选。
3. 在列表中区分赔案范围、原结案状态、原核赔金额和有效实付金额。
4. 打开详情查看事故、参与方和车辆、目标及关联赔案、保单和承保险种、损失、原理算/核赔/支付记录、资料缺口、原作业时间线和材料来源。
5. 从详情中的来源入口打开对应 PDF 页，无法定位到 PDF 的来源明确显示为结构化记录或来源不足。

本阶段不接入启动审查、AI/规则执行、疑点复核、补件、报告、案件录入或数据库导入。C01–C03 只用于查询和详情展示；不能因为数据文件中同时存在标准答案或复核脚本，就把这些内容暴露给应用或作为案件事实读取。

## 2. 当前实现检查结论

| 范围 | 当前实现 | 与本阶段需求的差距 |
| --- | --- | --- |
| 案件数据 | `cases/seeds.py` 硬编码两个 `CASE-2026-00x` V0 案件 | 未读取 C01–C03；对象关系和金额口径不足 |
| 案件 API | `GET /api/cases` 返回完整 V0 案件数组，`GET /api/cases/{id}` 返回同一结构 | 无查询条件、筛选、数据状态和面向详情的展示投影 |
| 前端入口 | 工作台侧栏直接展示两个 V0 案件 | 现有案件区域无查询状态、筛选和完整详情 |
| 详情能力 | `CaseSummary` 只展示申请金额、保单日期、条款版本和材料名称 | 无事故/赔案/保单/险种/损失/支付关系，也不能打开原材料 |
| 审查状态 | 工作台可列出现有 V1 分析任务 | C01–C03 尚未接入分析任务，最近审查状态应如实为“未启动” |
| 兼容性 | V0 案件结构被 Agent、会话快照、旧报告和既有测试使用 | 本阶段不应直接替换 V0 结构，否则会扩大到 Agent 和历史快照迁移 |

因此采用“新增只读结案案件模块、保留现有工作台链路”的增量方案。这样可以完成当前目标，同时不修改已稳定的 Agent、知识库、会话、事件流和旧报告协议。

## 3. 最小改动设计决定

### 3.1 数据边界

- 新增只读案件目录仓储，默认读取 `PROJECT_ROOT/test-data/claims-review/v1/inputs/*/case.json`。
- 只扫描 `inputs` 下的案件输入及其 `documents`；禁止读取 `expected`、`review-steps`、`variants` 和运行结果目录。
- 可增加一个可选环境变量覆盖输入目录，未配置时使用上述仓库内默认路径；本阶段不新增数据库表和导入命令。
- 应用响应只返回页面所需投影，不把整个 `case.json` 原样透传，也不在前端重新推导对象关系。
- 金额从整数分转换为带币种和状态的传输对象；未知、不适用和已知零元保持区分。
- 人伤字段在本阶段只表示原档案声明。`no_injury_reported` 展示为“原档案记录未报人伤”，不能展示为 AI 已确认“无人伤”。

### 3.2 与现有 V0 工作台隔离

- 保留现有 `/api/cases`、`V0ClaimCase`、`get_case()`、工作台和分析任务行为不变。
- 新增 `/api/review-cases` 资源承载 C01–C03，避免改变既有 Agent 的案件快照格式。
- 主导航保持“案件工作台”和“条款知识库”两个入口，不新增“案件查询”。
- 直接扩展现有工作台左侧“案件”区域：在原位置增加查询、筛选和 C01–C03 列表；选中案件后在工作台主区域展示摘要，点击“查看完整详情”进入独立详情页面。
- 现有历史分析任务仍可从工作台打开；打开历史任务时切回原有会话、任务和报告视图。
- 本阶段 C01–C03 详情不显示“启动审查”按钮。后续接入分析输入时，再设计从详情进入审查的转换和快照固定，不能复用 V0 按钮造成表面可点击、实际无法执行。
- 不引入 Vue Router，也不改变 `App.vue` 的主导航状态。

这是一项数据和协议层面的过渡隔离，不是新增产品入口：用户仍在同一个案件工作台操作，但 C01–C03 的只读详情与旧分析任务分别使用各自契约。这样避免本次查询功能修改 V0 Agent 的事实提取、规则、知识版本和历史报告。

## 4. 页面与交互

### 4.1 工作台案件查询区

查询区采用一行基础条件加一行筛选条件：

| 条件 | 交互与含义 |
| --- | --- |
| 查询类型 | 赔案号、报案号、车牌号三选一 |
| 关键字 | 去除首尾空格后匹配对应编号；忽略英文字母大小写，中文和符号按原值匹配 |
| 结案时间 | 起止日期，按目标赔案 `closedAt` 的本地日期包含边界筛选 |
| 人伤情况 | 全部、原档案记录未报人伤、有人伤、信息不足、信息冲突 |
| 审查进度 | 全部、未启动、执行中、待人工复核、待核实、车损审查完成、失败/待恢复 |

点击“查询”才发送请求；点击“重置”清空条件并重新读取全量 C01–C03。首期只有三案，不增加分页、排序配置、保存条件或模糊联想。

列表按最近结案时间倒序，稳定次序再按案件编号。每行展示：

- 案件编号及目标赔案号；多目标赔案逐行显示在同一单元格，不合并成一个虚构赔案号。关联赔案在次级信息中单独标明。
- 车牌并标明“本车/第三方”。
- 出险时间、目标赔案结案时间。
- 原核赔金额、有效实付金额两个独立列；未知时显示“未知”及原因，不用 `0` 代替。
- 原档案人伤标记。
- 最近审查状态；C01–C03 尚无对应任务时为“未启动”。
- “查看详情”操作。

### 4.2 查询状态必须分开

| 状态 | 页面表现 |
| --- | --- |
| 首次/重新加载 | 列表骨架或“正在加载案件”，不沿用旧结果冒充新结果 |
| 已加载但条件无匹配 | “没有符合当前条件的案件”，保留重置入口 |
| 数据尚未导入 | “尚未导入案件数据”，不显示为查询无结果 |
| 请求或数据加载失败 | 错误横幅和“重新加载”，不清除用户查询条件 |

切换到详情或快速连续查询时，继续沿用现有 `requestScope` 思路：取消旧请求，并在回调落地前检查当前请求归属，避免慢请求覆盖新条件或新详情。

### 4.3 工作台摘要与案件详情页

工作台摘要只展示出险时间、人伤原档案声明、最近审查状态、原核赔/有效实付金额、目标及关联赔案和车辆，不在工作台堆叠完整业务信息。左侧卡片只保留案件编号、主赔案号、车牌、结案日期和状态；长编号单行省略，完整内容通过悬停标题或摘要查看。

点击“查看完整详情”后切换到独立详情页面；顶部提供“返回案件工作台”，返回后保留工作台查询条件和选择。详情页面按以下顺序展示：

1. **案件概览**：案件编号、版本、事故编号、出险时间地点、目标赔案和关联赔案、范围限制、人伤原档案声明、最近审查状态。
2. **车辆与参与方**：本车和第三方分组，展示车牌、车辆角色、车主/驾驶人或关联人员；不把第三方资料混入本车。
3. **赔案及原处理结果**：每个赔案单独显示赔案号、报案号、目标/关联标识、结案类型、结案时间、原结论和原支付状态。结案状态与支付状态不合并。
4. **保单与承保险种**：交强险和商业险分组；每张保单展示取得状态、保险期间、被保险车辆；每个实际险种单独显示状态、限额/保险金额、免赔和适用条款版本。`available`、`not_obtained`、`not_insured`、`unrecognized` 使用不同文案。
5. **损失与金额**：按本车/第三方和损失项目展示申请、定损、确认金额，并关联赔案；不显示无口径的“案件金额”。
6. **原理算、核赔与支付**：展示计算结果、调整说明、审批金额、付款/退款/冲销记录、收款对象和交易状态。详情只陈述原记录，不在本阶段生成疑点结论。
7. **原作业时间线**：按事故发生、材料形成、核赔决定、支付事件、结案时间排序；每项保留记录类型、对象和来源入口。
8. **资料缺口与范围限制**：C03 的首次输入缺少商业三者险计算书必须可见，并明确这是“本次档案未取得”，不能显示为金额为零。
9. **材料目录**：支持按材料类别和关联对象在前端筛选；展示材料名称、类型、版本、取得状态、来源说明、形成/取得时间和关联赔案或对象。

每个有 `evidenceRefs` 的详情块提供“查看来源”。来源解析结果分三类：

- 案件 PDF：显示文件名、版本、页码和引用摘录；点击后通过受控 API 打开 PDF，并使用 `#page=<页码>` 定位。
- 结构化记录：显示记录来源和 JSON Pointer，不伪造 PDF 页码。
- 无可定位来源：显示“来源不足/无法定位”，不生成链接。

首期不做内嵌 PDF 阅读器、OCR、高亮框、全文搜索或缩略图；使用浏览器原生 PDF 新页打开即可满足当前材料查看目标。

## 5. API 契约草案

### 5.1 查询案件

`GET /api/review-cases`

查询参数：

| 参数 | 类型 | 约束 |
| --- | --- | --- |
| `queryType` | `claim_number \| report_number \| plate_number` | 有 `query` 时必填 |
| `query` | string | 最长 100，空白按未提供处理 |
| `closedFrom` | `YYYY-MM-DD` | 可选，包含当天 |
| `closedTo` | `YYYY-MM-DD` | 可选，包含当天；不得早于 `closedFrom` |
| `injuryStatus` | 受控枚举 | 可选 |
| `reviewStatus` | 受控枚举 | 可选 |

响应为对象而不是裸数组，以区分“数据未导入”和“查询无结果”：

```json
{
  "dataStatus": "ready",
  "items": [
    {
      "id": "C03",
      "revision": 1,
      "targetClaims": [
        {
          "claimId": "CLM-C03-COM-TP",
          "claimNumber": "DEMO-CLM-C03-COM-TP",
          "reportNumber": "DEMO-RPT-C03",
          "closureType": "paid_closed",
          "closedAt": "2026-06-15T16:30:00+08:00",
          "originalPaymentStatus": "settled"
        }
      ],
      "relatedClaims": [
        {
          "claimId": "CLM-C03-CTPL",
          "claimNumber": "DEMO-CLM-C03-CTPL",
          "reportNumber": "DEMO-RPT-C03",
          "closureType": "paid_closed",
          "closedAt": "2026-06-15T16:30:00+08:00",
          "originalPaymentStatus": "settled"
        }
      ],
      "vehicles": [
        { "vehicleId": "VEH-C03-A", "role": "insured", "plateNumber": "演示-C03A" },
        { "vehicleId": "VEH-C03-B", "role": "third_party", "plateNumber": "演示-C03B" }
      ],
      "accidentAt": "2026-06-08T09:10:00+08:00",
      "originalApprovedAmount": { "status": "known", "amountFen": 800000, "currency": "CNY", "reason": null },
      "effectivePaidAmount": { "status": "known", "amountFen": 900000, "currency": "CNY", "reason": null },
      "injuryStatus": "no_injury_reported",
      "latestReviewStatus": "not_started"
    }
  ]
}
```

`dataStatus` 仅有 `ready` 和 `not_imported`。目录或文件存在但无法解析、引用数据无法形成安全投影时返回统一错误响应，不把坏数据伪装成 `not_imported`。

金额仅汇总目标赔案：

- 原核赔金额来自目标赔案已批准的审批记录。
- 有效实付金额只计算目标赔案中状态有效且关系明确的付款，并处理其明确关联的退款/冲销。
- 状态或关联不足时返回 `unknown` 及原因，不进行猜算。

赔案号和报案号查询匹配该案件的目标及关联赔案；命中关联赔案时仍返回同一个案件，并保留目标/关联标识，不能把关联赔案改成目标范围。

### 5.2 查看详情

`GET /api/review-cases/{caseId}`

返回 `ReviewCaseDetail`，包含第 4.3 节页面所需的只读投影和已经解析好的来源引用。不存在返回 404。详情 DTO 保留稳定业务 ID，前端只负责分组展示，不根据数组位置建立关系。

为控制本次改动，不复制测试数据的整份 JSON Schema 到运行时传输层。后端只为实际返回字段建立严格 Pydantic DTO，并在投影时检查被引用的赔案、车辆、保单、险种、材料和证据是否存在。

### 5.3 打开案件材料

`GET /api/review-cases/{caseId}/documents/{documentId}/content`

- 仅允许读取该案件 `documents` 中状态为可用、具有相对路径且版本匹配的 PDF。
- 服务端解析并校验最终路径必须位于该案件目录内；不接受调用方传入文件路径，不允许 `..`、绝对路径或跨案件 documentId。
- 返回 `Content-Type: application/pdf` 和 `Content-Disposition: inline`。
- 未取得、路径无效、文件 hash 与清单不符或文件不存在时不返回内容；分别使用可理解的 404/409 错误。
- `#page=N` 是浏览器片段，不发送给服务端；页码来自证据记录，服务端不伪造。

| 案件 | 目标赔案 | 车辆范围 | 原核赔金额 | 有效实付金额 | 详情重点 |
| --- | --- | --- | ---: | ---: | --- |

## 8. 测试与验收

### 8.1 后端与契约

- C01–C03 均能加载；只读调用不会修改内存原值。
- 三种编号查询和三个筛选维度分别覆盖有结果、无结果和组合条件。
- 目标赔案与关联赔案不混入金额汇总；C03 返回 8,000 元核赔、9,000 元实付。
- C02 保持本车/第三方、交强险/商业险及各险种关系。
- `not_imported`、空查询结果、解析失败三种状态不混淆。
- 详情不存在、材料不存在、材料未取得、跨案件 documentId、目录穿越、hash 不一致均拒绝。
- 生成契约与 Python DTO 一致，前端对错误响应或缺字段不会静默接受。
- 既有 `/api/cases` 和 Agent/工作台测试保持通过。

### 8.2 前端

- 查询、重置、筛选以及从详情页返回工作台时保留条件和当前选择。
- 加载、无结果、未导入、失败四种状态分别渲染。
- 连续查询或切换详情时，旧请求结果不能覆盖当前选择。
- C01–C03 摘要的金额、人伤和状态文案准确；不出现未说明的“案件金额”。
- 工作台仅展示摘要；左侧长赔案号和车牌不造成多行挤压，完整信息在独立详情页展示。
- C02 详情能区分本车/第三方和交强险/商业险；C03 能看到关联赔案、金额差额原记录及资料缺口。
- PDF 来源链接包含合法 caseId/documentId；页码只在证据实际提供时出现。
- 执行契约检查、前端测试、构建和相关 API 测试。

### 8.3 本阶段验收口径

本阶段可以验证需求 A01，以及 A02、A03 中的只读展示部分；可以验证 A04 的“原档案人伤状态及来源可见”，但不能宣称已完成 AI 人伤识别。A05 以后涉及执行、复核或报告的验收项均不属于本阶段。

## 9. 明确不做

- 不把 C01–C03 标准答案、复核步骤或后补资料提前放入首次案件输入。
- 不将 C03 的金额差直接标成多赔、少赔或确认问题。
- 不实现启动审查、审查范围确认或输入快照固定。
- 不把 C01–C03 转成现有 V0 `V0ClaimCase` 以勉强运行旧 Agent。
- 不做数据库案件表、批量导入后台、权限、多租户、分页、导出、收藏或高级排序。
- 不做 OCR、内嵌 PDF 阅读器、全文检索、高亮或缩略图。
- 不新增主导航入口，不重构知识库或导航框架，不升级依赖，不顺手调整无关样式。
