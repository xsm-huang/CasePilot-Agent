# 启动审查与输入固定设计

状态：已实施  
日期：2026-10-28  
适用需求：`已结案车险赔案审查agent需求.md` 6.3  
适用案件：`test-data/claims-review/v1/inputs/C01` 至 `C03`

## 1. 目标

本阶段把 C01–C03 从“可查询、可查看详情”接入现有分析基础设施，并以结案车险审查作为唯一任务主线，完成以下闭环：

1. 启动前明确展示审查范围、保单与条款、已取得材料、人伤声明、资料缺口和可执行范围。
2. 服务端判断案件能否启动；全部不可执行时给出阻塞原因，部分资料缺失时只限制受影响项目。
3. 每次启动生成独立任务，并固定案件输入、材料版本、条款知识版本及运行配置。
4. 双击、超时重试或重复提交不能生成重复任务。
5. 相同资料重新审查必须由人员显式发起，新任务保留前序任务关系。
6. 人工补充证据以追加版本保存，可用于当前人工复核，但不修改原始输入和既有 AI 结果。
7. 如需 AI 使用补充证据，显式创建新的审查任务；原任务、原人工意见和原报告保持不变。

本设计只覆盖“启动审查与输入固定”。查询列表字段、详情页展示完整性和原作业时间线等既有差距不在本阶段顺手整改；唯一必要联动是案件启动后，查询列表的最近审查状态必须反映真实任务状态。

## 2. 设计原则

### 2.1 复用主链路，不建设平行系统

- 继续使用现有 `Conversation → Analysis → Command → Event/SSE → Review → Report` 生命周期和数据库基础设施。
- 继续使用 `/api/analyses`、幂等请求记录、任务 revision、事件序号、审核恢复和历史只读机制。
- 不新增 `review_analysis`、`review_event`、`review_report` 等平行资源，不复制任务状态机。
- C01–C03 直接使用统一的结案赔案审查输入，不再保留 V0 案件和旧任务的运行分支。
- 旧代码中可复用的幂等、事务、事件和恢复能力保留；旧案件 DTO、种子案件、旧报告读取及对应页面分支删除。
- 不让 Agent 从详情展示 DTO 反推业务关系；任务使用服务端构造的规范化审查快照。

### 2.2 原输入不可变，新增信息只追加

- `caseSnapshot` 在任务创建时一次写入，作为该任务的原始输入，之后不修改。
- 当前人工复核使用的补充证据保存在 `evidenceSupplements`，按版本追加，不合并回 `caseSnapshot`。
- 新任务可以显式选择前序任务和补充证据，构造新的输入快照；前序任务不回写、不重算、不替换报告。
- 页面查看历史任务时，以任务保存的快照和版本绑定为准，不以当前案件接口或当前知识库发布指针覆盖。

### 2.3 服务端形成权威快照

- 前端只提交案件 ID、预检得到的 `expectedInputVersion` 和可选前序任务 ID，不能提交整份案件内容。
- 服务端重新读取案件输入、核对引用关系、材料 hash 和知识版本，生成规范化快照及摘要 hash。
- `inputVersion` 使用规范化 JSON 的 SHA-256；数组顺序按业务定义固定，禁止使用文件修改时间或本机路径作为版本依据。
- 启动时输入已变化则返回 409，要求重新预检；不能在用户确认旧范围后静默使用新资料。

## 4. 启动前预检

### 4.1 预检内容

详情页点击“启动审查”后，先请求服务端预检并展示确认区：

| 区域 | 展示内容 |
| --- | --- |
| 审查对象 | 目标赔案、关联赔案、车辆、损失项目及明确的范围限制 |
| 保单与条款 | 交强险/商业险、实际承保险种、条款文档、版本、章节及知识绑定状态 |
| 材料 | 已取得、未取得、不可读取材料数量及受影响对象 |
| 人伤提示 | 原档案声明、已知伤者或信息冲突；不得将“未报人伤”升级为系统确认无人伤 |
| 可执行项目 | 可继续的检查项和对象 |
| 受限项目 | 无法确认的检查项、影响对象、原因及所需材料 |
| 阻塞原因 | 没有可识别审查对象或所有检查均不可执行时的明确原因 |

预检只整理事实和执行边界，不运行模型、不产生审查结论、不创建任务。

### 4.2 预检状态

`ReviewPreflight.status` 只有三种：

- `ready`：存在明确目标赔案，当前范围内的计划检查均可执行。
- `partial`：至少一项可执行，但部分检查因材料或条款不足被限制；允许启动。
- `blocked`：没有可识别目标赔案，或没有任何可执行检查；禁止启动并展示 `blockingReasons`。

技术依赖不可用与业务资料不足分开处理：数据库、模型配置等启动依赖失败使用标准错误响应；材料缺失、条款未取得等属于预检结果，不能伪装成 500。

### 4.3 可执行范围的最小模型

不在本阶段建设通用规则配置平台。预检返回简单、可追踪的 `scopeItems`：

```json
{
  "scopeItemId": "amount:CLM-C03-COM-TP",
  "kind": "amount_reconciliation",
  "entityIds": ["CLM-C03-COM-TP", "CV-C03-TP"],
  "status": "limited",
  "reason": "首次档案未取得商业三者险赔款计算书",
  "requiredMaterialTypes": ["calculation"]
}
```

`status` 仅使用 `executable`、`limited`、`blocked`。`limited` 表示其他项目仍可执行，本项只能输出“无法确认/待补充”；不能把资料缺失直接判断成业务问题。

C03 的商业三者险计算复核应为 `limited`，但事故、承保、支付记录和已取得材料的一致性检查仍可启动。

## 5. 输入快照

### 5.1 快照结构

任务的 `caseSnapshot` 统一使用 `ClosedClaimReviewSnapshot`，并包含明确的 `snapshotKind: "closed_claim_review"`。不再使用联合类型，也不保留 `V0ClaimCase`。

`ClosedClaimReviewSnapshot` 保存后续工具实际需要的规范化业务输入：

- 案件编号、案件 revision、准备时间和审查范围。
- 事故、参与方、车辆及本车/第三方角色。
- 目标赔案、关联赔案、结案和原支付状态。
- 保单、承保险种、条款引用及对象关联。
- 损失、理算、核赔、支付、退款/冲销关系。
- 材料清单、状态、版本、SHA-256、关联对象和证据定位。
- 人伤原档案声明、资料缺口和范围限制。
- 预检形成的可执行及受限项目。

不保存本机绝对路径、临时下载 URL、expected 答案、review-steps、variants 或运行结果。PDF 文件不重复写入任务 JSONB；快照保存不可变材料标识与 hash，材料读取仍通过受控案件材料服务并校验 hash。

### 5.2 知识版本绑定

任务统一使用 `knowledgeBindings` 数组，因为一个案件可能同时涉及交强险和商业险：

```json
{
  "documentId": "PA-CTPL-2020-CONTENT",
  "documentSha256": "...",
  "version": "2020修订内容",
  "sectionIds": ["CTPL-LIABILITY", "CTPL-SETTLEMENT"],
  "generationId": "已匹配的不可变知识 generation",
  "productCode": "CTPL",
  "clauseVersion": "2020修订内容",
  "embeddingProfile": "固定配置指纹"
}
```

绑定必须同时核对条款业务版本和文件 SHA-256，不能只按文件名或当前发布版本匹配。一个条款没有可用 generation 时，仅将依赖该条款的项目标为 `limited`；若仍有不依赖该条款的检查可执行，案件允许启动。

任务创建后只使用已保存的 generation，不重新查询当前 publication。后续知识库发布、重建索引或切换当前版本均不改变历史任务。

### 5.3 统一上下文

`AnalysisContext` 统一为：

- `inputVersion`
- `knowledgeBindings`
- `messageIds`
- `modelProfile`
- `promptVersion`

不再保留 `caseVersion + generationId` 的旧上下文，也不填充虚假的单一 `generationId`。工具只处理 `ClosedClaimReviewSnapshot`；任务状态机、事件、审核和报告生命周期继续复用现有实现。

## 6. API 与命令

### 6.1 预检

`GET /api/review-cases/{caseId}/review-preflight`

返回：

- `caseId`
- `expectedInputVersion`
- `status`
- `scopeSummary`
- `policiesAndTerms`
- `materialSummary`
- `injuryNotice`
- `scopeItems`
- `blockingReasons`

案件不存在返回 404；输入引用损坏或无法安全构造快照返回明确的数据错误，不降级为 `blocked`。

### 6.2 会话和任务创建

继续使用现有接口：

1. `POST /api/cases/{caseId}/conversations`
2. `POST /api/analyses`

会话创建服务只从结案案件仓储解析 caseId，不新增第二套 conversation API，也不再查询旧种子案件仓储。

`CreateAnalysis` 对结案案件增加：

```json
{
  "conversationId": "...",
  "kind": "initial",
  "question": "请审查当前已结案车险赔案。",
  "expectedInputVersion": "预检返回的 SHA-256",
  "predecessorAnalysisId": null,
  "supplementIds": []
}
```

首轮任务必须提交 `expectedInputVersion`；服务端重建快照并比较，不一致返回 409 `INPUT_VERSION_CONFLICT`。

### 6.3 幂等与并发

- 创建分析继续要求 `Idempotency-Key`。
- 相同作用域、相同 Key、相同请求返回第一次响应。
- 相同 Key、不同请求返回 409 `IDEMPOTENCY_CONFLICT`。
- 不同 Key 的重复点击由单会话活动任务约束拦截，返回 409 `ACTIVE_ANALYSIS_EXISTS`。
- 前端在首次请求结果不确定时保留原 body 和 Key；只有确认任务创建成功或用户改变输入后才丢弃。
- 预检不占用任务幂等记录，因为它不产生业务写入。

### 6.4 最近审查状态

`latestReviewStatus` 不再对 C01–C03 固定返回 `not_started`。查询接口根据该案件最近一条分析任务的权威状态映射展示；任务数据仍是唯一事实来源，不新增可漂移的案件状态字段。

## 7. 重新审查

“继续追问”和“重新审查”必须区分：

- 继续追问：沿用同一会话和固定输入，只创建 followup analysis。
- 重新审查：显式新建会话及 initial analysis，重新预检和固定输入。

重新审查时可提交 `predecessorAnalysisId`：

- 前序任务必须属于同一 caseId。
- 前序任务必须已存在；不要求前序任务成功完成，失败任务也可显式重审。
- 新任务保存前序任务 ID；前序任务不增加反向可变字段。
- 相同资料也必须生成新的 analysisId 和 input snapshot；不能复用前序任务充当新审查结果。
- 页面明确显示“重新审查”，不能因刷新、补充证据或知识库更新自动触发。

只保留直接前序关系，不建设通用任务 DAG、比较报告或版本合并界面。链路可按 `predecessorAnalysisId` 向前追溯。

## 8. 人工补充证据

### 8.1 追加模型

补充证据属于具体 analysis，不属于原始案件快照：

```json
{
  "supplementId": "...",
  "version": 1,
  "analysisId": "...",
  "title": "补充取得的商业三者险赔款计算书",
  "materialType": "calculation",
  "entityIds": ["CLM-C03-COM-TP"],
  "fieldPaths": ["calculations"],
  "sha256": "...",
  "addedAt": "ISO-8601",
  "addedBy": "当前操作者标识"
}
```

- 每次补充产生新的 `supplementId` 和递增版本，不覆盖同名文件。
- 文件先写入临时位置，完成类型、大小和 SHA-256 校验后原子移动到内容寻址目录，再提交任务元数据；失败不产生可见补充记录。
- 当前首期只接收 PDF，不做 OCR、编辑、删除或替换。
- `caseSnapshot` 和 `inputVersion` 保持不变；任务 revision 正常递增，并产生可重放的 `evidence.supplemented` 事件。

### 8.2 当前人工复核使用

补充证据加入后：

- 当前 AI 事实、疑点和报告内容不自动变化。
- 审核表单可以选择 supplementId 作为人工意见依据；审核记录保存引用的 supplementId。
- 页面明确区分“原始输入证据”和“审查期间人工补充证据”。
- 若没有可靠的当前操作者标识，不伪造人员姓名；实现阶段使用系统已有操作者上下文，缺失时明确标记为未识别操作者并限制正式验收。

### 8.3 让 AI 使用补充证据

点击“基于补充资料重新审查”时：

1. 新建会话和 initial analysis。
2. 记录原任务为 `predecessorAnalysisId`。
3. 将用户选定的 supplement 复制为新任务输入快照中的只读材料版本。
4. 重新计算 `inputVersion` 并重新绑定适用知识 generation。
5. 原任务及其人工审核记录不修改。

不支持在原 LangGraph checkpoint 上热插入材料后继续运行，避免模型上下文、已完成节点和报告内容失去一致性。

## 9. 页面流程

### 9.1 首次启动

1. 在案件完整详情页点击“启动审查”。
2. 页面加载预检结果。
3. `ready/partial` 展示确认按钮；`partial` 同时展示受限项目和所需材料。
4. `blocked` 禁用确认按钮，只显示阻塞原因和返回详情入口。
5. 用户确认后创建会话，再以同一请求 body 和幂等键创建分析任务。
6. 成功后进入现有任务工作台，通过快照和 SSE 展示状态。

不新增主导航、Vue Router、向导框架或多步骤表单。确认区复用详情页的已有信息组件，只增加预检结果和一个明确的确认操作。

### 9.2 历史任务

历史任务顶部展示：

- 案件编号和输入版本短标识。
- 原始输入材料数量和固定条款版本。
- 前序任务入口（如有）。
- 补充证据列表及其加入时间。

历史任务不得从当前 `/api/review-cases/{id}` 重新拼装案件摘要。

## 10. 持久化与事务边界

- 任务快照、创建命令、用户消息、幂等响应和会话上下文继续在现有一次数据库事务中提交。
- 结案案件快照继续存入 analysis JSONB，不新增只为复制同一快照而存在的表。
- `predecessorAnalysisId` 存在任务快照中，并在创建时校验同案关系。
- 补充证据元数据保存在任务快照的追加集合中；文件使用内容 hash 命名，避免重复保存相同字节。
- 文件落盘和数据库无法形成全局事务：采用“文件先原子落盘、元数据后提交”的顺序。崩溃最多产生无引用文件，不能产生指向不存在文件的已提交记录；无引用文件清理不属于本阶段主线。
- 不修改现有知识 publication；任务仅保存被绑定 generation ID。

## 12. 实施顺序

### 第一批：主线启动闭环

1. 冻结预检、schemaVersion 2 快照和统一上下文契约。
2. 后端预检与结案案件输入构建器。
3. 复用现有会话、任务创建、幂等和持久化链路。
4. 详情页启动确认及进入现有任务工作台。
5. 最近审查状态改为从真实任务派生。
6. 完成 C01、C02、C03 的端到端启动、刷新和历史读取测试。

### 第二批：需求内的版本补充

7. 显式重新审查及前序任务关系。
8. 人工补充 PDF、审核引用 supplement。
9. 基于补充资料创建新任务。

两批都属于 6.3；第一批完成前不插入列表美化、详情关系补全、报告比较、批量操作等优化工作。

## 13. 测试与验收

### 13.1 预检与快照

- C01、C02 能形成明确目标范围；C03 缺少计算书时为 `partial` 而非 `blocked`。
- 构造无目标赔案或无任何可执行输入的夹具时返回 `blocked` 和明确原因。
- 快照包含完整对象关系、材料版本/hash 和多条款绑定，不包含本机路径及预期答案。
- 预检后修改案件 revision、材料 hash 或条款绑定，启动返回 409，不静默使用新输入。

### 13.2 幂等与持久化

- 相同 Key/相同请求只创建一个任务并返回相同 analysisId。
- 相同 Key/不同请求冲突；不同 Key 并发启动同一会话也只能产生一个活动任务。
- 服务重启后任务使用相同案件快照和知识 generation；当前知识发布变化不影响已经创建的新任务。
- V0 案件 API、旧任务读取和旧页面入口均已移除；数据库残留旧版本记录不会被当作当前任务读取。
- 新任务的审核、恢复、SSE 和报告生命周期回归通过。

### 13.3 重新审查与补充证据

- 相同资料只有显式重新审查才创建新任务，并保存 predecessorAnalysisId。
- 补充证据只追加版本；原 inputVersion、AI 结果和审核历史不变化。
- 当前人工审核能引用补充证据，引用不存在或不属于当前任务时拒绝。
- 基于 supplement 重新审查产生新 inputVersion 和新任务；原任务仍可按原快照完整读取。

### 13.4 前端

- 启动确认完整展示范围、条款、材料、人伤、受限项目和阻塞原因。
- `partial` 允许启动，`blocked` 不允许；错误状态不伪装成业务阻塞。
- 双击和不确定响应重试复用同一幂等键。
- 切换案件、返回详情或打开历史任务时，迟到请求和 SSE 不覆盖当前选择。
- 启动后查询列表不再显示“未启动”，状态来自对应任务。

## 14. 明确不做

- 不在本阶段补齐 6.1 列表全部字段或重做列表布局。
- 不在本阶段补齐 6.2 的全部关系展示、字段级来源和完整原作业时间线。
- 不建设案件导入后台、通用文档管理、批量启动、定时审查或规则配置平台。
- 不做补充证据编辑、删除、覆盖、OCR、病毒扫描平台或在线 PDF 标注。
- 不自动重跑 AI，不自动合并报告，不提供报告差异比较。
- 不建设任务 DAG；只保存直接前序任务关系。
- 不新增主导航、路由框架、任务子系统或数据库 ORM。
- 不修改原赔案状态，不执行支付、补赔、退款或重新开案。
- 不迁移、不展示、不恢复旧 V0/V1 任务和旧演示案件；如需保留数据，仅在实施前做离线备份，不进入运行兼容逻辑。

## 15. 完成判定

本阶段只有同时满足以下条件才可标记完成：

1. C01–C03 均可从详情页经过预检创建真实持久任务。
2. 预检正确区分 ready、partial、blocked，C03 的局部缺失不阻断其他检查。
3. 案件、材料和多个条款版本被固定，历史任务不受当前数据和知识发布变化影响。
4. 重复提交不会产生重复任务。
5. 显式重审保留前序关系；补充证据不改写原输入，AI 使用补充证据时创建新任务。
6. 废弃功能已删除，API、契约、前端、数据库、重启恢复及浏览器主流程测试全部通过。

本设计已按第 12 节顺序实施；超出第 14 节边界的工作另行安排。
