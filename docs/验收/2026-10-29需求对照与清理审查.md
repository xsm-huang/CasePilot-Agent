# 需求对照与文件清理审查

审查日期：2026-10-29。基准：[已结案车险赔案审查 agent 需求](../需求/已结案车险赔案审查agent需求.md)。

本次检查当前工作区，包括已修改和未跟踪的新代码，不仅检查 HEAD。未修改业务代码、原有文档或删除文件。设计文档作为背景，不作为功能已经完成的证据。

## 1. 总体判断

当前项目已经具备可运行的首期演示主流程：查询案件 → 详情与材料 → 启动预检 → 固定输入 → 六节点实际执行 → 发现与逐条复核 → 阶段/最终报告 → 显式重审及更正。

不能据此认定需求全部交付。主要缺口是：审查覆盖仍有按阶段汇总的粗粒度判断；人伤识别与共用事实依赖尚未形成完整结构化闭环；资料分类与维护入口不完整；部分证据关联和历史原始文件访问存在缺陷；真实效果验收工具与当前主流程已经脱节，缺少当前版本的真实样例评估结果。

这里区分三种情况：有代码且回归通过、只实现部分业务要求、尚无实现或验收证据。没有用页面存在、提示词存在或测试替身通过来替代业务效果验收。

## 3. 已确认的需求差异与缺陷

### D01 人工新增发现可能丢失补充材料关联（优先修复）

对应需求 6.7.2、A07/A11/A18。`manual_finding` 接受并校验 `supplementIds`，但构造发现时仅保留 `factRefs`、`citationRefs` 等字段；`ReviewCheck` 本身没有补充材料引用字段。仅引用补充 PDF 的人工发现可以创建成功，生成的发现却没有证据关联。

本次直接调用业务方法复现：输入 `supplementIds=['s']`、其他引用为空，结果发现的 `factRefs=[]`、`citationRefs=[]`，且不存在 `supplementIds`。任务仍保存该附件，但发现与附件的关联没有保存。应修复契约、持久化、卡片与报告中的对应关联。

依据：`analyses/review_actions.py:72`、`schemas/agent.py:53`。

### D02 必要检查覆盖不够细，尚不能保证各损失及险种都审查完

对应 2.2、6.4—6.5、7.3、A03/A15。确定性金额检查已按赔案/计算书执行，但材料、条款与金额解释的 AI 必要检查仍主要是 `consistency:assessment`、`clauses:assessment`、`amount:assessment` 三个阶段汇总项。

模型返回某阶段非空、全部 supported 的 `checkedItems` 即可将该阶段汇总项标为 passed；服务端没有逐项核对这些返回值是否覆盖本次所有车辆、损失、险种和必要事实。C02 虽包含三个目标赔案及多个险种，条款必要计划仍只有一个阶段汇总项。另有 AI 发现仅引用正文字符串时，`enrich` 无法从该字符串解析对象/保单/险种，可能留下空的对象关系。

应建立按实际损失、承保险种及共用事实生成的必要计划，并验证模型结果对计划的覆盖和归属。现有最终门禁是有效基础，但其可靠性受检查计划粒度限制。

依据：`analyses/review.py:17`、`:66`、`:200`；`workflow/agent_nodes.py:382` 附近的阶段完成判断。

### D03 人伤四态识别与共用事实阻塞尚不完整

对应 2.3、A04/A05。原档案四种声明可以保存/展示；规则能对部分文字生成范围外人伤提示，专业转交记录也已实现。但没有把原声明、材料线索与冲突合并为独立的系统人伤识别结果，列表及预检仍主要使用 `declaredStatus`。

材料规则依赖少量正则。本次验证：`伤者：张某，诊断：挫伤` 能识别；`第三方乘客受伤后到医院急诊治疗，医疗费800元` 没有命中该规则。此结果仅证明确定性规则遗漏，不能推断真实模型一定遗漏。

共用事故时间、责任等尚未形成“冲突事实 → 受影响车损项目 → 必须解除的未决条件”的结构化依赖。若模型漏报，现有门禁不会自行发现这一遗漏。需要补人伤综合四态、身份不确定性、冲突证据和相关车损阻塞测试。

依据：`analyses/checks.py:51`、`:302`；`analyses/review.py:169`、`:200`；`analyses/review_input.py:115`。

### D04 材料缺失、格式错误与跨来源冲突的规则覆盖不足

对应 6.5.1、A07/A19。闭案分支的规则主要读取预先准备的 `dataGaps`；`observations` 被统一转为待核实项。并未实现完整的按具体索赔项目推导必要证据、逐字段提取来源值并区分缺失/格式/冲突的规则链。

同文件中旧数据结构的日期检查在闭案分支提前 return 后不会执行。当前日期由 `datetime.fromisoformat` 直接解析，本次将事故日期改为格式错误值后得到 `ValueError`，而非独立、可复核的格式错误检查结果。AI 可补充材料核对，但不能据此认定规则已覆盖全部要求。

依据：`cases/evidence_rules.py:25`、`analyses/checks.py:81`、`:144`。

### D05 条款版本隔离已实现，险种章节适用性与语义支持仍需补强

对应 6.5.2、A03/A08。已通过 generation、产品代码、版本以及文件 hash 固定检索范围；引用 ID 与逐字摘录也有校验。当前工具未使用绑定中的 `sectionIds` 限制检索章节；校验未验证引用属于该具体损失/险种的适用章节。

同一商业条款文件中的其他险种条文可能有合法 ID 且存在相应摘录。摘录存在不能证明推断受到支持。这部分仍依赖提示词、模型判断及人工复核，尚缺当前版本的真实语义验收。应补错误险种章节、合法引用但不支持结论、批单影响等样例。

依据：`workflow/tools.py:63`、`analyses/evidence.py:85`、`:143`、`workflow/prompts.py`。

### D06 金额与支付属于基础核对，未覆盖全部业务关系

对应 6.5.3、A09。有效支付已处理成功/失败、退款和冲销，计算书支持明确算式。重复检查主要捕捉相同 `externalTransactionId`；没有完整的跨不同交易号、同一损失重复计入检查。收款人字段会展示，但收款授权关系、复杂合同参数及完整计算规则并未形成确定性核对体系。

AI 会核对金额口径和调整说明；金额差异仍作为疑点而非自动确认错误，这一点符合需求。尚不能宣称已经完成通用赔款复算或专业定损。

依据：`analyses/checks.py:177`、`:257`、`:286`；`workflow/prompts.py`。

### D07 上传与资料维护尚未达到三类管理要求

对应 6.9、A17/A18。知识库上传主要填写 `productCode`、`clauseVersion`；缺少保险公司、资料来源、明确文件分类、适用信息等完整元数据。案件专属保单/批单和证据没有统一的维护、版本及重绑操作。

演示案件可通过准备 `case.json + PDF` 导入，但没有应用内结构化录入/导入表单。补充证据虽然支持 API 中的材料类型和对象参数，工作台却固定发送 `materialType='review_evidence'`、`entityIds=[]`，由后端默认归到目标赔案，无法在上传时准确指定车辆或损失项目；上传表单也没有来源字段。

依据：`api/knowledge.py:58`、`schemas/knowledge.py:46`、`cases/review_repository.py:27`、`WorkbenchPage.vue:70`、`useWorkbench.ts:206`。

### D08 历史快照保留，但原始案件 PDF 未建立独立版本归档

对应 6.3/6.8/6.9、A08/A18。历史任务保留输入、正文事实与报告快照；补充 PDF 按 hash 保存。原始案件材料则仍从当前案件目录解析，再验证其是否与任务快照的 hash 相同。

当前文件被替换后会明确拒绝打开，避免误用新版，这是正确保护；但系统没有据旧 hash 找回旧 PDF 的路径，不能保证历史引用的原始文件持续可访问。需补内容寻址归档及版本保留机制。

依据：`analyses/workspace_service.py:162`、`workflow/tools.py:36`、`cases/review_repository.py:543`。

### D09 页面信息与人工操作细节有缺口

对应 6.1/6.6—6.8。案件列表只显示案件号、车牌、结案日期和进度，缺少列表要求的出险时间、原核赔/支付金额、人伤标记；这些数据部分已在 API/当前案件卡片中提供。

报告弹窗只有条款 `citationRefs` 的查看按钮，未把固定快照中的事实引用、补充材料逐项呈现为可打开的原始证据入口。转专业动作要求接收方和说明，但未强制关联“已提供材料”；操作者由服务端统一环境变量配置，适用于固定人员演示，不能在多人共用同一实例时可靠区分实际操作人。

依据：`WorkbenchPage.vue:104`、`ReviewReportDialog.vue:25`、`analyses/workspace_store.py:591`、`:45`。

### D10 范围外案件的限制主要依赖输入声明

对应 2.1。当前演示输入均为 paid_closed。范围限制文字能够展示，但没有看到按拒赔、零赔付、全损、盗抢、诉讼等案件类别自动匹配可执行规则与限制的完整机制。增加这些输入时，应保证未提供相应专业规则的部分明确受限，不会沿用普通碰撞流程产生范围过大的结论。

依据：`analyses/checks.py:36`、`analyses/review_input.py:47`、`test-data/claims-review/v1/inputs/`。

### D11 真实验收工具与当前版本脱节（优先修复）

对应第 9—10 节、A20。`tests/evaluation/reports.json` 仍引用 `CASE-2026-001/002`，当前输入为 C01/C02/C03。`scripts/evaluate_v1.py` 创建任务未提供当前要求的 `expectedInputVersion`，最终确认未提供 `coverageConfirmed/reviewCycleId/reportVersion/basisHash`，且仍检查旧的三个模型报告节点。当前报告已改成业务记录汇总，旧判断标准不适用。

因此不能只等待模型服务恢复就直接运行旧评估；需先适配案件、契约、复核流程与验收判据。现有 `docs/验收/本轮真实验收/results.json` 为 blocked，reports 为空，人工语义审查为 pending，不能支持当前效果通过的结论。

当前 C01/C02/C03 分别覆盖正常本车、多险种正常与资料不足/金额异常，尚缺需求规定的人伤混合、共用事实冲突等专用端到端样例及真实标注对照结果。现有模拟测试不等于这些真实效果验收。

依据：`tests/evaluation/reports.json:2`、`scripts/evaluate_v1.py:83`、`:351`、`schemas/workspace.py:385`。
